## 0. 先给判决

**事实**：hongzhao 在 openKylin 单机这一个场景里，交付完整度高于我们。它跑了 5 款真实智能体、有沙箱、有显著性检验、有标注集自评、有全套治理文件。在这些轴上追赶是几个月的工程量，追平也只是"另一个 hongzhao"。

**判断（本规划的地基）**：它有一个结构性的、无法靠加班补掉的弱点——**它的可信度建立在特权上**：需要 root、systemd 瞬时单元、自建 `hz_egress`、防火墙脚本、`sudo hongzhao-setup`、`.deb`。这套东西绑死 Linux + openKylin，出不了这个环境。所以它**天然做不到"全平台"**，不是不想做，是它的可信模型不允许。

SIXDIM 反过来：方法完备到能在纸上跑，但**零黑盒通用性、零实测**。

于是唯一能"对标甚至超过"的轴是清晰的：

> **一份平台中立的评测协议（spec）+ 一个不需要任何特权就能成立的参考实现。**
> 可信性来源从「我把它关进沙箱了」换成「我的证据链任何人都能离线复核」。

这是从"工具"升级成"标准"的路径，也是我们唯一能做出对方做不了的动作的地方。

**翻转条件（什么时候该放弃这个定位）**：如果目标生态明确只认 openKylin 单机、且使用者只按交付完整度买单，那这条路不划算，应退回功能追赶。这条判断需要你再确认一次目标场景，规划里所有优先级都挂在这一条上。

## 1. 先看一眼终点：一次理想的接入长什么样

（先给具体使用轨迹，再谈约束——否则规划会变成一堆无法验证的形容词。）

```bash
# 任意 OS、任意账户、不装任何东西、不给 root
agentlitmus probe --command "hermes acp" --name hermes
#   → 探测出：ACP✓ 会话可重置✓ 记忆快照✗ 工具调用可观测✓  ⇒ 接入档位 T1+T3
#   → 生成 agents.hermes.yaml，并明写："本次可评分维度 6/6，置信层级 T3（部分维度降档）"

agentlitmus run --agents agents.hermes.yaml --suite standard --out out/hermes-01
#   → out/hermes-01/manifest.json      运行契约：用例集 sha256 + 规则版本 + 环境指纹
#   → out/hermes-01/evidence.ndjson    五类证据统一流，每条带 sha256 前缀
#   → out/hermes-01/report.html        首屏：综合分 + 95%区间 + 覆盖率 + 置信层级 + 不可判清单

agentlitmus regrade out/hermes-01      # 换了规则版本，不重跑，离线重评，逐条列出裁决变化
agentlitmus compare out/hermes-01 out/hermes-02   # 版本回归；有显著回归或新增红线 ⇒ 退出码非零，可接 CI
```

这份轨迹里，我们今天**只有第 3 行的前半段做得到**。下面所有阶段都是在把它补齐，并且顺序有讲究。

## 2. 现状盘点：我们真正有的 vs 我们声称有的

### 2.1 ⚠ 一个必须先处理的诚信问题

**事实**：`Evidence.java:11-45` 定义了四类证据（dialogue / memory / action / artifact），README 写的是"把对话、记忆记录、行动轨迹、产物统一组织为证据"。但：

- 真实智能体路径 `DialogueBenchmarkRunner.java:115-159` 只产出 `Evidence.dialogue`（×5）和 `Evidence.artifact`（judgment、transcript，×2）。
- `Evidence.memory` 只出现在 `MemoryBenchmarkRunner.java:88-108`，而那条路径测的是**我们自己的** `FileLongTermMemory`（内置 baseline 智能体），不是被测对象。
- `Evidence.action` 在整个 `src/main/java` 下没有任何调用点。

**判断**：对 KylinBot / Hermes 这类真实智能体，我们只有对话证据。"四类统一证据"这句话现在是不成立的，而这恰好是对外承诺里"基于运行证据"的核心表述。**这是比任何功能缺失都严重的风险——被追问一次就会连带质疑其他所有声明。** 两条出路，选一：

- (a) 立刻改口径：README 明写"真实智能体当前采集对话 + 判定产物；记忆/行动证据为路线图 T2/T3 层"。（半小时）
- (b) 把 `Evidence.memory` 真做出来（见阶段 2）。

建议先做 (a) 止血，(b) 按阶段推进。**不要什么都不改。**

## 3. 取精华 / 去糟粕

### 3.1 从 SIXDIM 取（方法论层，都是小改动能拿到大的可信度提升）

1. **三值语义**：判定结果必须是 `0 / 1 / unknown`，且 **unknown 永远留在分母里，不许静默丢弃**。这条直接解决我们当前的污染问题——超时、429、空回答现在被当成 0 分算进通过率。
2. **识别区间**：给 unknown 记为 `[0,1]`，于是每个维度分数天然带一个下界/上界对（悲观/乐观），报告可以写"该维度 44%–56%，因为 6 条不可判"。比 bootstrap 便宜得多，先做这个。
3. **反事实增量 Δ**：同一道题跑"有记忆"臂和"无记忆"臂，只有超出对照的部分才归因于记忆。**这是"通过率 67%"唯一有意义的解释方式。**
4. **证据契约测试 + 负向对照测试**：为"证据格式"本身写测试（HZ 是 12/12，SD 是 10/10 反向对照）。我们现在的 4 个测试类里没有任何一个验证证据流可被复核。
5. **终态产物绑定**：断言"某文件内容"必须绑定在同一次动作里（对象 + 参数 + 路径/hash 同一事件），禁止跨事件拼接推断。**这条是我们未来做"任务复用"维度断言时的设计红线。**
6. **统一版本口径**（SD 自己踩的坑，作为教训取）：设计时轴、代码持久化时轴、`RET_nowait` 三套版本口径互不背书。**从第一天就把版本号绑进证据格式**，别留三个。

### 3.2 从 hongzhao 取（工程与统计层，按性价比）

1. **`oracle` 神谕对照**：失败题再问一次、附上正确事实；答对 → 卡在记忆环节，仍错 → 基座/执行问题不算记忆分。**这一条直接把我们 `FailureCause` 的"推断"升级成"观测"，性价比最高。**
2. **`doctor` 能力探测 + 分档接入**：探测 ACP、跨会话重置、记忆存储位置（在状态目录里 grep 随机标记，文本或 SQLite 都找）、工具可观测性。**全平台路线的入口就是它。**
3. **记忆状态快照 M**：能读到被测对象的记忆落盘内容，才能判"到底写没写进去"。见 2.1，这是我们的证据缺口本体。
4. **系统层证据 vs 自报工具调用**：HZ 用内核 eBPF 进程连接器记真实 exec。我们跨平台做不到 eBPF，但可以用**本地等价物**（Linux `bwrap` + 包装脚本、macOS `sandbox-exec`、Windows Job Object / Procmon 式审计日志），或者干脆降级为"只记自报，并在报告里明写这一层不可信"。
5. **逐族区分度 `discrim` + 准入门槛**：永远全对的题是废题，应该踢出分母并公示。我们 150 条里必然有一批这种题，**做一次就知道有多少**。
6. **同题配对 + bootstrap 区间 + "区间含 0 不下结论"**：我们现在说 "KylinBot 67% > Hermes 47%" 是没有任何统计含义的。
7. **评分器自评（gold set + 第二标注 κ）+ 评委裁决缓存**：证明"尺子自己是准的"。评委缓存让重新评分可复现，这一条几乎免费。
8. **manifest + sha256 + 实体全虚构**：运行契约可账对；虚构实体防止基座模型靠预训练知识蒙对（我们的用例里有真实职业名、IP 段之类，需要审一遍）。
9. **`compare` 退出码非零接 CI**：智能体版本升级后回归一次就有结论。这是从"一次性评测"变成"持续评测"的唯一开关。
   （本仓库的 `ci.yml` 挂在 `workflow_dispatch` 上**手动触发**，不挂 push：额度由人决定，不由提交决定。）
10. **治理文件全套**：SPEC / ROADMAP / CHANGELOG / SECURITY / CONTRIBUTING / CODE_OF_CONDUCT。一个下午的事，外部使用者眼里的"能不能进生态"信号。
11. **它踩过的事故要当我们的教训**：HZ README 明写"首轮正式运行中，智能体与评测框架共用账户，曾在宿主家目录中执行破坏性操作"。我们的 `CommandAnswerer` 现在就是这个状态（裸 `ProcessBuilder`，继承当前用户全部家目录权限）。

### 3.3 明确不取（糟粕）

| 来源 | 不取什么 | 理由 |
|---|---|---|
| SIXDIM | 完整区间数学栈、每维四臂、层级化固定权重 `arm_Z/family_value/dimension_A` | 复杂度失控，且它自己承认没跑出过真实六维分数；我们没有任何一个数字能填进这套权重 |
| SIXDIM | 让 LLM 参与主判定链的形式化仲裁 | 与"判定本身不引入新不确定性"的既有设计原则冲突 |
| hongzhao | root + systemd 瞬时单元 + 自建 `hz_egress` + 防火墙脚本 | **平台锁死**，与全平台定位直接矛盾；且要求目标机有特权 |
| hongzhao | 46 族生成式题库 | 体量锁死；我们的静态可读用例是差异化资产，不该换掉 |
| hongzhao | 评委专用 Key 随安装包分发 | 把凭据打进 deb 是可商榷的安全模式，别照抄 |
| hongzhao | 报告八个视图 | 维护面过大；我们做 3 个视图（评分卡 / 逐条证据 / 诊断）就够 |
| 我们自己 | `frontend/`、`out-*`×8、`__pycache__`、`cron-*`、`send_email.py` + `email_config.json` | 仓库卫生；**注意 `email_config.json` 落库前先查有无凭据** |

## 4. 分阶段优化点

每段都写：问题 / 做法 / 落点（具体类） / 成本 / 验收 / 风险。成本是**推算**，按单人、熟悉本仓、业余时间的一半效率估。

### 阶段 0 —— 清账与口径修正（1 天，无条件先做）

- 把 2.1 的措辞问题改掉：README 与 `SOLUTION.md` 里"四类证据统一"改成如实描述当前层级。
- `.gitignore` 补 `out-*/`、`__pycache__/`、`frontend/node_modules/`；确认 `email_config.json` 内容后决定是否脱敏移除。
- 新增 `CHANGELOG.md`、`SECURITY.md`、`CONTRIBUTING.md`；把本文件拆成 `ROADMAP.md`（只留阶段表）+ `SPEC-DIRECTION.md`（留判断与取舍）。
- 风险：无。收益：答辩时"你自己代码里有什么脏东西"这一问有答案。

### 阶段 1 —— 让已有数字变可信（3–5 天，最高性价比）

**1.1 三值判定语义**（落 SIXDIM 精华①③）
- 问题：超时/429/空回答现在计为失败，污染通过率；`Outcome` 五类里 `OMISSION` 吸收了"没答"和"答错"两种完全不同的事实。
- 做法：`Judgment` 增加 `Verdict { PASS, FAIL, UNKNOWN }`（`passed` 保留为派生便捷方法）。`CaseJudge` 里所有"无法判定"的出口——空回答、无响应、`MODE_DEGRADED`、LLM 调用异常回退——统一产出 `UNKNOWN` 而不是 `FAIL`。
- 落点：`core/Judgment.java`、`core/CaseJudge.java`（现 `judgeByLlm` 的 catch 分支与 `causeOf` 的 `text.isEmpty()` 分支）、`report/ReportRates.java`、`HtmlReport`。
- 验收：内置 `reference` 仍 100%；重跑 KylinBot/Hermes 的既有 `evidence/*.jsonl` 离线重评，通过率**上升**且新报"覆盖率 147/150"，两个数字都能对上历史失败清单。
- 风险：**会改变 README 里已发布的四个实测数字**。要么同时重出材料，要么在报告里并列"旧口径/新口径"。别悄悄改。

**1.2 运行覆盖率 + 上下界**（三值语义的自然产物）
- 做法：每维报三个数——`通过 / 已判定`（有效分）、`已判定 / 计划`（覆盖率）、`悲观下界 = 通过/计划`。第一版**不做 bootstrap**，用这个便宜的区间对（SIXDIM 的 I(unknown)=[0,1] 直接给出来的）。
- 落点：新增 `report/CoverageRates.java`（注意与现有 `dataset/CoverageReport` 区分命名：一个是**数据集**覆盖，一个是**运行**覆盖，别混）。

**1.3 复现契约 manifest**
- 做法：每次运行写 `manifest.json`：`{ 用例集 sha256, 判定规则版本, 智能体配置三元组(id/框架/适配器版本), JDK 版本, OS/arch, 参数(重复次数/并发/超时), git commit }`。报告首屏展示，并允许 `litmus verify --run DIR` 重算哈希对账。
- 落点：`evidence/EvidenceCollector`（每条证据带 `seq` 与内容 sha256）、新增 `report/RunManifest.java`、`Cli` 加 `verify` 子命令。
- 成本：1 天。收益：README 里"完全可复现"从口号变成可对账文件。

**1.4 证据格式契约测试**（落 SIXDIM 精华④）
- 做法：一组测试固定"一份合格 `evidence.ndjson` 长什么样"，字段缺失/序号断裂/hash 不匹配必须失败；再加**负向对照**：故意投毒一条证据（改掉答案文本），断言重评结果必须变化。
- 落点：`src/test/.../evidence/EvidenceContractTest.java`、`CaseJudgeNegativeControlTest.java`。

### 阶段 2 —— 接入协议化：全平台的地基（1–2 周）

**2.1 能力声明 `AgentCapability`**
- 问题：真实智能体的可观测深度差异极大，用同一套口径评分必然产生假数字。
- 做法：`Answerer` 增加 `capabilities()`：`RESETS_CONTEXT`（能清会话保长期记忆）、`MEMORY_INSPECTABLE`（记忆可读）、`TOOL_CALLS_VISIBLE`（ACP 工具事件）、`ARTIFACTS_VISIBLE`（产物可取）、`TRANSPORT`（cli/acp/http/stdio）。用例在 `run` 前按能力过滤，报告首屏写"本对象可评维度 4/6，置信层级 T1"。
- 落点：`agent/Answerer.java`（唯一抽象点，改动集中）、`MemoryCase` 增加 `requiredCapability` 字段、`MultiAgentBenchmark` 做能力协商。
- **关键设计判断**：不要"能跑就跑、跑不动算失败"。能力不足要从分母里**显式移出并公示**，而不是变成 0 分。这是与 SIXDIM unknown 语义的一致做法，也是我们相对 HZ 的深化点。

**2.2 `probe` / `doctor` 接入向导**
- 做法：给定一条命令或 ACP endpoint，自动跑 3 条探测题（随机标记 → 重置 → 再问；工具事件观察；状态目录 grep），产出配置草稿 + 档位。
- 落点：新增 `probe/ProbeRunner.java`、`Cli` 子命令 `probe`。状态目录扫描先只支持"文本 + SQLite"两种（照抄 HZ 的做法，验证过有效）。
- 成本：3–5 天。收益：**接入新平台从"写 Java 类"降到"填一行命令"**，这是"适合全平台"的实际含义。

**2.3 记忆状态证据（补 2.1 的缺口）**
- 做法：`MEMORY_INSPECTABLE` 的智能体在每回合前后做快照（目录 diff + SQLite dump），产出真 `Evidence.memory`；有了它，`PERSIST_MISSING` 从推断变成观测——能直接看到"根本没落盘"还是"落盘了但没答出来"。
- 落点：`memory/` 包新增 `MemorySnapshotter`，`FailureCause` 文档同步改写（现在的"黑盒只能推断"这段前提会被部分推翻，注释要改）。

**2.4 无特权隔离（安全必需，且刻意不做 systemd）**
- 问题：见 3.2⑪，`CommandAnswerer` 现在是裸 `ProcessBuilder`，继承当前用户全部权限。
- 做法（分层，全部无需 root）：
  - 通用兜底：**独立临时 HOME + 环境白名单 + 只挂载本场景目录的视角 + 硬超时 + 整组回收**（子进程组 kill，防孙子进程逃逸）。所有 OS 都能做。
  - Linux：有 `bwrap` 就叠加（用户命名空间，不需 root）。
  - macOS：`sandbox-exec` profile。
  - Windows：受限令牌 / Job Object。
  - 全部退化为"仅临时 HOME"时，报告里明写隔离层级，不许静默降级。
- 成本：2–3 天做到"临时 HOME + 进程组回收 + OS 专属叠加层"。
- 风险：**这是唯一一条我不建议推迟的**。评测对象在你的开发机上跑破坏性操作，出的是一次事故不是低分。

### 阶段 3 —— 让判定本身可自证（1–2 周）

**3.1 oracle 二遍（照抄 HZ 最好的一招）**
- 做法：FAIL 用例自动重问一次，把该题 `expectedContains` 作为已知事实注入提问；答对 ⇒ 记 `MEMORY_STAGE`（确实卡在记忆），仍错 ⇒ 记 `BASE_OR_EXEC`，并从记忆分母剔除。
- 落点：`DialogueBenchmarkRunner` 增加第二遍回合（只在 FAIL 上触发，成本可控），`FailureCause` 新增 `BASE_OR_EXEC` 类归因。
- 成本：2–3 天。**这条单独就能把"你的归因是猜的"这个致命质疑变成"我的归因有对照实验"。**

**3.2 关键词判定的等价变体**
- 问题：`expectedContains` 是精确子串，回答里换个说法就判遗漏——这是自动评测最容易被攻破的地方（HZ 也为此修过题：「回答用了『不吃辣』却被判遗漏」3 条）。
- 做法：`MemoryCase.expectedContains` 从单个 String 改为可接受变体列表 + 规范化（简繁、全半角、数值/单位、"客户关系管理专员"↔"负责客户关系管理"）。`validate-cases` 强制列出变体并警告"只有一条写法的题"。
- 落点：`core/MemoryCase.java`、`dataset/MemoryCases.java`、`CaseJudge`。
- 风险：**别把 LLM 塞进主判定链**——那会同时丢掉"完全离线确定性"这个我们仅存的差异化资产。需要语义判定的题，用 `requiresLlmJudge` 现有分支，且报告里单独统计 LLM 判定占比。

**3.3 标注集 + 一致性 κ**
- 做法：人工标 30–60 条真实回答（含边界写法），跑规则层和"规则+评委"，报一致率与 κ；目标 ≥90%。把这批样本入库为 `data/goldset.yaml`，加进 `mvn test`。
- 落点：新增 `dataset/GoldSet.java` + `selftest` 子命令。
- 成本：1 周（大头是人工标注）。收益：唯一能回答"尺子准不准"的东西。HZ 用 135 条 + 第二模型盲标做到 κ 0.86/0.92，这是可比较的硬指标。

**3.4 评委缓存与指纹**：LLM 裁决按 (rubric hash + 回答 hash) 缓存；`selftest` 记录模式、代码提交、标注集 sha256、评委指纹。离线重评结果必须不变。成本：半天。

### 阶段 4 —— 让题目有意义（1–2 周）

**4.1 区分度准入 `discrim`**：全参照智能体都过的题 = 无信息量，标为 `low-discrimination` 并移出主分母（不移出数据集，只公示）。先跑一次，看 150 条里有多少废题——**这个数字本身对外部使用者很有说服力**，因为它说明你在审自己的题。

**4.2 对照臂**（落 SIXDIM Δ + HZ 对照探针）：`MemoryCase` 增加 `controlVariant` 字段——同题但**从未注入任何记忆**的版本。只有 `p(T) − p(C)` 超出对照组的部分才算记忆能力。我们的 20 条跨会话用例正好是做这件事的最小起点，改造成本极低。这是把"67%"变成有因果含义的数字的唯一办法。

**4.3 实体全虚构**：审一遍现有 150 条，把真实职业名/常见 IP/公开事实换成虚构但同构的实体，防基座靠预训练蒙对。成本低，一天。

**4.4 补数据缺口**：`CoverageReport.java:64` 已经自曝"更新×边界交叉用例缺失"。再补：安全档（高敏留存、要求删除、声明作废、临时方案、记忆投毒）、压力档（长更新链、同构干扰、规模档）。**注意**：不要为此改成生成式题库，静态可审是我们的定位。

**4.5 长时程档**：HZ 有 1/4/8 周档但明写"成本高，默认不选"。我们做**时间跳跃模拟**（不真的等，而是给被测对象一个带未来时间戳的档案）作为便宜替代，并在报告里明写它是模拟不是真实长时程。判断：诚实的模拟 > 沉默的缺失，也 > 烧 3 小时的真实长跑。

### 阶段 5 —— 统计与回归（1 周）

- **同题配对比较**：跨智能体对比只在"共同可判定"的题上做配对，bootstrap 95% 区间，区间含 0 明确写"未见显著差异"。落点：新增 `stats/PairedCompare.java`（自己实现，零依赖，B=1000 固定种子）。
- **重复运行稳定性**：已有 `--repeat N` 和 `StabilityReport`，补 HZ 那个更好的指标——**同题一致率**（每次都过 / 时过时不过 / 每次都败），比 σ 直观得多。
- **`compare` + CI 退出码**：两次运行逐题比对，输出回归/改进/新增红线；有显著回归时非零退出。这一步之后，工具从"评测一次"变成"守着版本"。

### 阶段 6 —— 全平台交付（2 周，跨平台定位的真正兑现）

**判断：这一阶段才是"超过 hongzhao"的地方，前五个阶段只是追平。**

- **协议先行**：把证据格式、判定语义、能力档位、manifest 字段冻结成 `docs/SPEC-EVIDENCE.md` + JSON Schema。允许别人用 Python/Go/Rust 写 runner，只要产出合格 `evidence.ndjson` 就能进我们的评分器。**"适合全平台"的完整含义是跨 OS + 跨语言 + 跨智能体框架，而不是"我也支持 macOS"。**
- **平台适配矩阵**（每格都要实测过，不能只写"应该能跑"）：

| 平台 | 隔离手段 | 记忆快照 | 系统层证据 | 状态（2026-10-24 实测口径） |

这几格都需要真机，编不出来也不该编。当前能诚实说的是：协议跨语言，工具在 Linux x86_64

## 6. 验收：怎么知道我们真的追上或超过了

不要再用"通过率"当唯一指标。换成这七个，每个都能自测：

1. **可评层数**：接入一个新智能体能自动识别到 T几（目标：不写代码就到 T2）。
2. **运行覆盖率**：已判定/计划（目标 ≥97%，且不可判清单可点开逐条看原始证据）。
3. **归因证据化比例**：`FailureCause` 中由 oracle/快照/行动证据支撑的占比（目标：从 0 → ≥80%）。
   已实现为 `core/AttributionEvidence`，每次 `run` 输出到 `report.txt` 与 `attribution.json`。
4. **题目区分度**：低区分题数量与占比（第一次跑这个数字本身就是材料）。
5. **评分器一致性**：gold set 上 κ（目标 ≥0.85）。
6. **复现对账**：`litmus verify --from DIR` 全部哈希一致；同配置两次运行逐条判定一致（内置智能体 σ=0 已经做到，真实智能体要报一致率）。
7. **跨平台格数**：阶段 6 那张表里**实测过**（不是"理论上能跑"）的格子数，目标 6/7。**当前 3/8**
   （宿主 x86_64 / 容器 / JVM 17），其余格子缺真机，不拿"理论上能跑"充数。

第 7 条是判胜负的那一条：hongzhao 在这一行是 1（openKylin）。我们在这一行做到 5 以上，"全平台评测基础设施"这个定位才成立，超过它才不是嘴上说的。

### 验收现状（2026-10-24，口径 `2026.10-c`）

| # | 目标 | 现状 | 达标 |
|---|---|---|---|
| 1 | 不写代码到 T2 | 配置里给 `stateDir` 即升到 T2（内置 degraded 实测 T2）；不给则如实停在 T1 | ✅ |
| 2 | 覆盖率 ≥97% | reference 100%、degraded 98.9%（full 283）；不可判逐条可点开原始证据 | ✅ |
| 3 | 归因证据化 ≥80% | 已实现统计口径（`AttributionEvidence`）。**记忆注入模式 full 283：degraded 162/162 = 100%**（边界泄漏 113、旧值未更新 30、相近混淆 10、召回缺失 6、需语义判定 3，逐条挂在记忆快照上）。**但这一格是最容易的**：记忆由框架写入、逐条可读。对话模式且不给 `stateDir`、不加 `--with-oracle` 时，依赖快照的归因一律记为未证据化，比例会掉到很低——这是设计意图，不是缺陷 | ✅ 口径已建立 |

| 4 | 低区分题占比 | 每次 `run` 报告尾部自动给出，全过/全败/全不可判的题被点名 | ✅ |
| 5 | κ ≥0.85 | 评委层（qwen-plus）**κ 0.901**；规则层 κ 0.636（弃权率 32.1%，开口即对率 97.4%，盲点 0） | ✅ 评委层达标 |
| 6 | verify 全哈希一致 | full 283 双智能体运行 **1138 份产物全部一致**（含 `attribution.json`，它在契约之前落盘所以自己也被哈希）；跨 JVM（17 vs 21）`report.txt` sha256 逐字节相同；内置 σ=0。**这一格曾经假绿过**：加完归因层和记忆召回后，283 题集上 `report.txt` 已经逐次不同了，而内置智能体的 σ=0 断言照样通过——因为它只比判定结果，不比整份产物。是跨 JVM sha256 那道闸门抓出来的。两处根因（不可变 Map 的随机迭代序、召回同分依赖墙钟）见 `PITFALLS.md` §8.8 | ✅（本轮重验） |
| 7 | 跨平台 6/7 格 | **3/8**（宿主 x86_64 / 容器 / JVM 17）；`.deb` 已在 openKylin 宿主实测安装（含空 `PATH`、无 locale 环境下的控制台编码） | ❌ 缺真机 |

只剩第 7 条没达标，而它不是"做没做"的问题：要 arm64 / macOS / Windows / 信创 / ssh 的真机。
**在拿到真机之前，对外只说 3 格。**

第 3 条虽然口径已建立，但**别拿 100% 当结论**：那是记忆注入模式下的数，记忆逐条可读，
归因天然是观测事实。真正要盯的是对话模式那一格——真实智能体的记忆在它自己内部，
不给 `stateDir`（升到 T2）或不加 `--with-oracle` 时，`report.txt` 会如实写出
"未证据化 N 条（引用这些归因时需注明是推断）"。**指标能掉下去，它才是指标。**

第 6 条本轮学到的一件事：可复现性不能靠"内置智能体 σ=0"来宣布，只能靠**跑两次比字节**，
而且要在最大题集上比。demo 4 题集上两次一致，说明不了任何事——随机迭代序要几十条记录才撞出来，
墙钟同分要在同一秒内写完才会显形。断言"判定结果一致"也说明不了任何事：`report.txt` 里的
归因段、证据顺序、雷达图数据都不在判定结果里。**要么比整份产物的哈希，要么别说"可复现"。**

## 7. 主要风险

- **口径变更会推翻已发布数字**（阶段 1 直接改通过率算法）。处理：新旧口径并列一版，别悄悄换。
- **能力分档可能被读成"给自己台阶下"**。处理：分档必须同时公示"该档缺什么、为什么缺、怎么补"，并让**我们自己**的内置智能体也受同样约束。
- **全平台矩阵的每一格都要真机验证**，没有 Mac / Windows / ARM 机器就是纸面声明——这跟 SIXDIM 的问题同构。**开工前先确认手上有哪些真机**。
- **范围**：七个阶段单人做是半年。这份规划的价值在于顺序，不在于全部做完；任何时刻停下来，前面阶段都已让产品更可信。
