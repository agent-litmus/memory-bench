# AgentLitmus 后续发展方向（草案）

> 状态：内部讨论稿，未定版。
> 输入：现有代码与实测数据 + 竞品《openKylin 作品六维判分的审计原理与实现》（2026-10-15）的对比分析。

## 0. 总定位（一句话）

**做"跑通的黑盒评测基础设施"，不做"没跑通的完美方法论"。**
竞品用 31 页证明了严谨的代价是永远交付不完；我们的护城河是已实测四款智能体、
零依赖、deb 一键装。后续所有投入必须先过一道闸：**是否增强"可信的实测数字"这个核心卖点**。

## 1. 立即必做（低成本，直接堵住质疑）

### 1.1 unknown 单列：无响应不再计入分母 ⭐ 最高优先
- 现状：超时/空回答按失败计，README 自己承认污染真实智能体分数。
- 已有半成品：`FailureCause.NO_RESPONSE` 已把无响应归因单列，只差报告层。
- 改法：报告输出双指标——**有效分 = 通过 / 已判定数**，**known_coverage = 已判定 / 计划数**。
  雷达图用有效分，表格附 coverage。约 1~2 天（report 包 + HtmlReport/CompareTable）。
- 借鉴点：这是竞品三值逻辑（0/1/unknown、unknown 保留分母）里唯一值得立刻搬的语义，
  且我们的实现成本远低于它。

### 1.2 仓库卫生
- `out-*`×8、`frontend/`、`__pycache__`、`cron-*`、`send_email.py`+`email_config.json` 移出主仓或进 .gitignore。
- 第一次 clone 的人第一眼看的就是工程素养。半天。

## 2. 短期（1~2 周，测量效度补强）

### 2.1 同题双臂：零成本拿到因果归因 ⭐ 战略级便宜
- 竞品的对照臂（T/C 注入中性历史）思想很重，但它的实现绑定白盒夹具；我们黑盒下有更轻的版本：
  **跨会话用例天然支持"同题两问"**——注入真实历史问一次（T），注入等量中性历史再问一次（C）。
- 产出 **Δ_记忆 = p_T − p_C**：回答"答对到底靠长期记忆还是靠模型先验/检索碰运气"。
- 现有 20 条跨会话用例直接复用，MemoryCase 加一个 `control` 变体字段即可。
- 这是对竞品最有力的正面回应：**它的因果思想我们吸收了，而且是在真实智能体上跑出来的。**

### 2.2 关键词判定的假阴性治理
- 现状：`expectedContains` 单串包含，措辞不同即误判失败（竞品审计点名了这一漏洞类别）。
- 改法（规则优先原则不动摇）：`expectedContains` 扩为**等价变体列表**（任一命中即过），
  由 `validate-cases` 校验变体不互相矛盾；内置 150 条逐条补 1~3 个变体。
- 明确**不**做 LLM 裁判化：`requiresLlmJudge` 保持现状、默认关，离线可复现是卖点。

### 2.3 协议版本锚点（防"口径漂移"）
- 竞品被自己的版本分歧拖死：设计文档、共享协议、候选实现三套口径无法互相背书。
- 我们趁早立规矩：报告头部写入 **protocol_hash（用例集 + 判定规则的 SHA256）**，
  规则或题库变更即换 hash，跨版本分数禁止直接对比。一天工作量，永久免疫此类质疑。

## 3. 中期（1~2 月，从"尺子"到"平台"）

### 3.1 任务复用（t 维）终态工件断言
- 竞品"说了不算，要看落盘工件"的判定是真升级。黑盒下唯一可落地的位置就是 t 维：
  让 t 类用例要求被测智能体**产出文件**（写配置/生成报告），runner 校验文件存在 + 内容断言。
- CommandAnswerer/ACP 通道天然能执行；`MemoryCase` 加 `artifact_assertions`。
- 做完后 t 维从"嘴上复用"变成"行动复用"，六维中第一个行为级证据维度。

### 3.2 接入生态 = 真正的护城河
- 评测工具的价值不在代码在**被测方数量**。ACP 通道已验证（Hermes），下一步：
  - 把 `hermes-acp` 适配器泛化为**通用 ACP answerer**，接入任意 ACP 智能体零代码；
  - 提供 `litmus probe --command "..."` 自检子命令：3 条用例验证适配器通不通，降低接入门槛；
  - 目标：KylinBot / Hermes / 第三个国产智能体 + 任意 HTTP 端点，**榜单 ≥5 款**。
- 每款智能体版本迭代时重跑全量 → **回归报告**（StabilityReport 已有一半），
  这是"办公场景持续评测"的故事起点，也是 deb 装机量的留存理由。

### 3.3 人类一致性抽检（效度证据，不是功能）
- 抽 30 条真实智能体回答人工标注，报规则判定与人类的一致率（预期 ≥90%）。
- 一页纸 + 一个数字，答辩时"规则判定可信吗"的终结回答。竞品声明了这个门槛但没做——我们做了就是差异化。

## 4. 明确不做（防泥潭清单）

| 不做 | 原因 |
|---|---|
| 全量反作弊控制门（manifest 哈希绑定、材料根拒写、跨臂 case_hash 校验） | 威胁模型不成立：被测方是外部智能体，碰不到题库；评测端自用 `--repeat` + git 锚点已够 |
| 区间数学 / 识别区间聚合 | 输出 null 点分的工具没有用户；覆盖率指标（1.1）拿走 90% 价值，10% 成本 |
| 每维四臂全套对照 | 2.1 的同题双臂拿走核心论证，全臂化成本指数上升 |
| LLM 裁判进主判定链 | 摧毁"零 API Key、σ=0"两大卖点 |
| frontend/ 复活 | Vue 原型与 CLI 交付重复，雷达图 HTML 已满足演示需求，删 |

## 5. 优先级总览

| 方向 | 价值 | 成本 | 建议时点 |
|---|---|---|---|
| 1.1 unknown 单列 + coverage | 高 | 1~2d | 立即 |
| 1.2 仓库卫生 | 中 | 0.5d | 立即 |
| 2.1 同题双臂 Δ_记忆 | **很高** | 3~5d | 第 1~2 周 |
| 2.2 判定变体治理 | 高 | 2~3d | 第 1~2 周 |
| 2.3 protocol_hash | 中 | 1d | 第 1~2 周 |
| 3.1 t 维工件断言 | 高 | 1~2 周 | 第 3~6 周 |
| 3.2 通用 ACP + 榜单 | **很高** | 持续 | 并行推进 |
| 3.3 人类一致性抽检 | 中 | 3d | 有真实数据积累后 |

> 排序原则：先让已有数字更可信（1.x），再让数字更有因果含义（2.x），
> 最后让工具长出别人没有的东西（3.x）。任何时点，能跑、可复现、有数 优先于严谨度提升。
